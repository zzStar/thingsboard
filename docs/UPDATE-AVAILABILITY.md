# 智工物联低中断更新与持续采集设计

设计日期：2026-10-15。状态：单机软件改造已实现，设备现场改造和集群阶段待实施。本文件基于当前仓库配置、发布脚本和已记录的生产运行结果；本轮未连接服务器、未变更线上配置、未部署。实际入口和限制见[操作说明](UPDATE-RUNBOOK.md)。资源数值为历史记录，实施前重新测量。

## 1. 推荐路线与范围

分三阶段推进：

| 阶段 | 建议 | 能达到的目标 | 仍存在的边界 |
| --- | --- | --- | --- |
| A：单机优化 | 先实施，保留当前服务器 | 将备份移出普通发版停机窗口；发布失败可恢复；大屏保留数据；具备缓存的设备补报 | Java 重启仍有停机；内存队列不能承诺消息不丢 |
| B：双实例更新 | 扩容并完成集群兼容验证后实施 | 新版启动期间旧版服务继续运行；兼容更新逐节点切换；持久队列保存待处理消息 | MQTT/WebSocket 下线节点的连接需要重连；同机仍有宿主机故障风险 |
| C：跨主机可用性 | 业务规模或容灾要求提高时实施 | 应用节点跨主机；独立数据库、队列和入口，降低单点影响 | 数据库、队列、入口本身也必须有冗余，不能只加第二个应用 |

本次优先设计 A，B 为明确的演进路径。B 采用两台逻辑应用节点组成集群，可用蓝绿槽位管理版本，但更新时一次只替换一个节点。不直接复制当前 in-memory 应用并共享数据库；不在 3.5 GiB 主机上叠加两套应用及 Kafka；暂不引入 Kubernetes。

“无中断”拆为四项分别验收：网页/API 可访问、长连接可恢复、采集数据完整、统计最终一致。页面仍能打开不代表设备消息已经落库；缓存补报期间统计可能延迟。

## 3. 发布分类：先判断能否在线更新

每个候选版本生成发布清单，记录镜像 digest、源码提交/未提交变更摘要、官方 schema、产量扩展 schema、API 与队列格式兼容范围、基础配置摘要、可回退版本、验证报告和备份标识。秘密、JWT 和大屏密钥不得进入清单。

| 类别 | 判断条件 | A 阶段路径 | B 阶段路径 | 回退方式 |
| --- | --- | --- | --- | --- |
| compatible | 无不兼容 DDL；旧版可读取新版写入的数据；API/消息兼容 | 在线备份后短暂停机替换 | 逐节点更新 | 回旧镜像，保留现有数据库 |
| additive | 新增可选字段/表，旧版仍能运行 | 经验证的显式迁移；无法确认则维护窗口 | 独立迁移任务先扩展，再滚动更新 | 兼容确认后只回应用，保留新增结构 |
| breaking | 删除/重命名字段、改变计数语义、上游要求停机升级 | 维护窗口 | 维护窗口或先拆成兼容版本 | 经验证的恢复方案，必要时恢复数据库 |
| infrastructure | PG 大版本、队列切换、存储或网络拓扑变化 | 独立运维流程 | 独立运维流程 | 对应基础设施恢复方案 |

普通更新不得顺带升级 PostgreSQL、Caddy 或改持久化目录。`tb_schema_settings` 相同只能作为必要检查，不能单独决定自动回退。设计新增产量扩展迁移版本及兼容声明；迁移只在明确的任务中执行，避免所有节点启动时自行跑未知 DDL。

发布方填写兼容声明，工具检查结构差异和版本范围，预发布环境验证新旧版本混跑。未知兼容性默认进入维护路径，不自动尝试滚动。

## 4. A 阶段：单机发布流程

### 4.1 准备期间旧版继续服务

1. 本地构建生产 UI 和 linux/amd64 镜像，执行独立空库 smoke test；针对本次变更运行必要测试。
2. 推送不可变标签，远端下载应用镜像并锁定 digest；核对目标架构、配置、磁盘空间和可回退旧镜像。
3. 获取发布锁，读取当前实际应用镜像、容器状态、基础服务版本及数据库 schema。基础服务应已健康；普通发版只检查，不执行会重建它们的 up。
4. 备份文件大小、磁盘占用按现有数据量估算；空间不足在停止应用前拒绝。磁盘余量至少覆盖新旧镜像、一次完整备份、临时文件及运行日志，由测量值计算。
5. compatible 更新在旧版运行时执行单进程 `pg_dump -Fc`，限制备份并发，设置连接/锁等待超时；与迁移、回算和 DDL 操作协调。备份失败或明显影响生产延迟时中止发布，旧版保持运行。
6. 备份写入临时文件，验证返回码、非空、目录可读、SHA-256，完成后原子落盘；附带旧版 digest、兼容清单、配置摘要和备份开始/结束时间。

PostgreSQL 的 pg_dump 能在应用并发读写时生成一致性快照，适合作为普通更新前的在线备份，但会增加磁盘/数据库压力，DDL 锁也需处理。[PostgreSQL 18 文档](https://www.postgresql.org/docs/18/app-pgdump.html)

在线备份只覆盖快照中的数据；备份后写入不在该副本中。普通应用回退不恢复数据库，避免丢失这些新写入。涉及迁移时仍需停写后最终备份，并记录可恢复边界。

`pg_restore --list` 只证明归档目录可读取，不证明完整可恢复。首次改造验收及后续重要升级前，需在独立数据库完整恢复并核对业务数据。文件存储、配置和必要秘密另行备份，数据库快照不自动覆盖文件一致性。禁止用完整生产副本向真实设备、邮件或外部集成发送消息。

### 4.2 切换窗口

1. 在稳定入口开启维护状态：API 返回 503 和 Retry-After，不用 200 的维护 HTML 代替 JSON；健康检查使用专用内部路径。设备 HTTP 接口明确失败，让客户端缓存重试。
2. 阻止新回算任务，等待现有回算到达检查点；为停止过程设置上限。回算是否能自动续跑需改造验证，不能将当前 cursor 字段当成完整续跑能力。
3. 优雅停止旧应用，记录停止时间；预期 MQTT/WebSocket 会断开。不要宣称等待 60 秒就必然排空内存队列。
4. 仅替换 thingsboard 容器，保留 PostgreSQL、Caddy、数据库卷及应用持久化数据。不会重复 install，不执行 down -v。
5. 等待内部就绪，并完成数据库查询、关键读 API 和专用测试设备的数据写入/读回检查。测试设备与生产设备分离，令牌不写日志。
6. 验证通过后关闭维护状态，检查公网 HTTPS、登录会话和 MQTT 授权连接/遥测落库。生产已有系统必须 READY，ACCOUNT_REQUIRED 只允许首次初始化。
7. 进入观察期，连续检查错误率、内存、设备重连和采集积压；通过后原子更新 current/previous，并保留本次阶段日志。

单机正常更新的设计预算为 90–180 秒不可写窗口，需用生产相似环境测量确认；不承诺 30 秒内完成。新版启动默认最多等待 300 秒，超时后按兼容条件恢复旧应用，回退启动也需要时间。不能为了缩短数字强行下调 Java 内存或跳过健康检查。

### 4.3 大屏与静态资源

- 断线保留最后产量，隐藏实时速度，显示更新时间与重连状态，恢复后刷新；首次打开失败也继续重试。先确认这些功能实际部署到线上。
- A 阶段已打开的大屏可保留画面，但停机期间首次访问仍可能得到维护提示。
- B 阶段将静态文件从应用更新中分离，由稳定入口提供；为每个版本保留带 hash 的静态资源，旧页面的懒加载资源继续可访问。
- HTML 不长期缓存；带 hash 的 JS/CSS 可长期缓存。匿名看板 API 保持 no-store，不在代理层缓存含设备信息的响应。
- 旧前端可能长时间打开，因此 API 兼容至少覆盖上一发布版本，必要时更长。资源保留建议至少 7 天并结合实际页面生命周期调整。

## 5. 采集数据保障：必须从设备端闭环

### 5.1 缓存与补报协议

设备或采集网关为每条采集记录写入本地持久化缓存，包含设备身份、原始采集时间、启动/计数周期标识、递增序号、totalCount 和 speed。先落本地缓存，再尝试上报；恢复后以原始时间补报，不统一改成重连时间。

重连建议指数退避 1、2、4、8 秒至最多 30 秒，并带随机抖动；新采集和历史补报公平调度，限制补报速率，避免全部设备恢复时压垮数据库。缓存满时显式告警，不能静默覆盖。

默认设计缓存 24 小时。按 2 秒一条，为每设备 43,200 条/天；按每条 200–500 字节估算，约 8.6–21.6 MB/天，另加索引、日志和至少 30% 余量。这是容量示例，实际采样字段、设备数量和存储寿命需测量。

MQTT PUBACK 或 HTTP 接收成功不能未经验证就认定产量表已经持久化。需要核对当前 transport→queue→rule engine→遥测库→产量表的确认边界。优先设计专用采集确认协议：按设备返回已经持久化的连续序号，只有端到端确认后才能清理缓存。无法改协议时保留最近 24 小时可重放窗口，结合落库核对后清理，并将数据完整性列为有条件目标。

QoS 1 提供重传能力，仍需幂等；QoS 0、仅 RAM 缓存或没有补报能力的设备，不承诺重启期间的数据完整。仅加 TCP 代理不会把消息持久化。

### 5.2 与产量算法的关系

当前产量以 totalCount 差分计算，并支持下降识别清零、迟到修正和相同设备/时间防重。补报必须维持原始采集时间；设备同毫秒多条采集或时钟倒退要在协议层明确处理，不能让不同记录误合并。

只看到停机前后两个累计值，在没有清零时可能恢复总增量，但分钟、班次分配只能估算；断线期间发生清零/多次换单，累计值可能永久丢失中间产量。完整逐条缓存及重放是恢复准确统计的基础。

原始遥测落库与产量计算不是一个已证明的跨模块原子事务。设计增加修复任务：扫描部署/故障影响区间，按原始 totalCount 重算并防重；保留前置基线及后继读数。跨设备按小批次执行，避免和实时处理争抢资源。不能只从 production_sample 最大时间开始，否则较早缺口可能被跳过。原始数据已过期或从未收到时明确标记无法恢复。

## 6. B 阶段：扩容后的集群与更新

### 6.1 容量与拓扑

4 核、8 GiB 仅作为双应用、数据库同机且 Kafka/共享缓存外置时的压测起点。两应用容器当前上限合计约 4.5 GiB，加数据库、代理、系统和备份压力后余量有限；不能认为 8 GiB 足以运行全部中间件。若全部同机，应先对 12–16 GiB 方案压测，最终规格按测量决定，不在本轮购买资源。

```text
浏览器 / HTTP设备 → Caddy稳定入口 → 应用A / 应用B
MQTT设备          → TCP稳定入口   → 应用A / 应用B
                                       ↓
                         Kafka持久队列 + 共享缓存
                                       ↓
                              PostgreSQL + 文件存储
```

- Kafka 作为 ThingsBoard 内部队列；Redis/Valkey 用于共享缓存。节点服务 ID 唯一，并按当前分支集群要求核对发现、分区重分配与内部通信；不能只设置 TB_QUEUE_TYPE 就认为集群已配置完成。
- 单 Kafka broker 可解决应用重启时的队列持久化，但不能抵御 broker/磁盘故障。严格容灾需要多副本、确认策略和独立故障域，或经验证的托管服务；不能把单 broker 包装成完整高可用。
- 所有应用节点共用数据库，文件使用验证过的共享存储或对象存储；每节点日志、临时文件和实例文件独立，不能盲目共享当前整个 app-data 卷。
- 队列、数据库、缓存和内部发现端口不公开；多服务器通过私网互通。MQTT TCP 入口候选为 HAProxy，现有 Caddy 保留 HTTP 职责。
- 初次从 in-memory 切 Kafka/集群属于 infrastructure 迁移，需要一次独立维护窗口、缓存补报及回退演练；不会凭空变为零停机。

官方架构将 Kafka 用于生产集群，内存队列用于单节点等场景，并描述了跨节点消息和共享缓存。具体参数以当前分支源码与预发布测试为准。[ThingsBoard 架构文档](https://thingsboard.io/docs/pe/reference/architecture/)

### 6.2 双节点发布顺序

1. 发布锁和在线备份完成，确认旧/新应用兼容；另一节点单独承担全部业务时仍有容量余量。
2. A 节点从新连接/请求分配中摘除，B 继续提供服务；给 A 上的 HTTP 请求和长连接一个有限排空窗口。
3. MQTT/WS 不能原地迁移。到达窗口后关闭 A 上的连接，客户端重连到 B 并补报；停止 A 前确保 Kafka 已确认发送的消息和消费者检查点按配置持久化。
4. 将 A 更新到候选镜像，等待就绪、集群注册、分区稳定和跨节点业务探测通过，再逐步恢复流量。
5. 观察候选节点至少 10 分钟，确认队列积压可下降、错误率正常、产量没有重复或缺口。
6. 用同样流程更新 B；每次最多一个节点不可用。更新结束后保存节点版本和入口状态，再提交 release。
7. 候选 A 失败则摘除 A 并恢复旧版；尚未更新的 B 持续服务。发生不兼容迁移或消息格式变化时不自动回退。

蓝绿全量切换可在资源允许时用于候选验证，但备用节点启动后可能已经参与消费、定时任务和写库；“未接收网站流量”不等于“没有副作用”。普通方案优先逐节点更新，避免临时第三个完整应用的资源峰值。

### 6.3 HTTP、WebSocket 与 MQTT 切换细节

- 新流量只进入就绪节点；就绪状态需覆盖 DB、队列、集群状态，不能只看进程或 8080 开放。
- Caddy 使用配置校验后 reload；上游健康探测及安全 GET 重试。写入 POST/控制指令不得默认自动重试，除非有幂等键和明确处理语义。
- Caddy reload 默认可能关闭 WebSocket，设计评估 stream_close_delay，结合节点排空窗口和浏览器抖动重连验证；不能单凭 reload 无停机就宣称 WS 不断线。[Caddy 反向代理文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- MQTT TCP 入口仅接收新连接并选择健康节点，摘除节点时保留已有连接直到排空上限；后端进程停止后原连接仍会断开。
- 保留同一域名/1883，避免改设备地址；初次将当前宿主机 1883 从应用交给 TCP 入口有端口交接窗口，需维护迁移。
- 会话、RPC、共享缓存失效和 WebSocket 跨节点订阅必须测试；粘性路由不能替代集群一致性。
- 若未来要求后端更新时设备 TCP 连接也持续存在，需独立稳定 transport/broker 和核心处理服务的拆分设计。当前双单体不能满足“任何连接都不重连”。

## 7. 产量模块的集群改造门槛

已存在的保护：建表事务 advisory lock、设备行 FOR UPDATE、样本冲突处理、回算 job_id 条件更新。它们提供良好基础，但只据此不能宣称已完成集群验证。

实施 B 前必须完成：

1. 两应用同时接收相同遥测、重复消费、迟到补报和配置保存，验证总量、分钟及班次汇总一致；验证事务重试和锁等待边界。
2. 回算任务加入节点归属、数据库租约/心跳与代次标识，过期接管后旧执行者不得继续推进新任务；按数据库限流保证全局并发，不沿用每 JVM 两线程等于全局两任务的假设。
3. 发布摘除时暂停领取新回算任务，当前任务存检查点；验证设备删除、配置修改、重启和任务接管交错。
4. 将产量 DDL 纳入明确迁移版本、兼容性检查；启动阶段只验证已就绪结构，或执行经批准的幂等兼容初始化。
5. 匿名大屏密钥仍在共用数据库里，域名、路径、校验与 no-store 不变；各节点和服务重建后原链接有效，重置/停用在所有节点一致。
6. 单位立即生效、班次未来生效、speed 键、历史查询和导出在不同节点一致；保留权限和租户隔离。

## 8. 发布状态、失败处理与回退

设计持久状态：PREPARING → BACKED_UP → DRAINING → STARTING → VERIFYING → OBSERVING → COMMITTED；失败进入 FAILED、RESTORING 或 MANUAL_RECOVERY。每一步记录时间、节点、digest、备份、流量目标及错误；通过临时文件＋原子替换落盘。

SSH 中断或部署进程退出后，重试先核对真实容器、入口和数据库状态，不只依赖 current 文件，不重复 install 或迁移。迁移前先记下 MIGRATION_STARTED，未知完成状态必须人工核对。

| 失败位置 | A 阶段处理 | B 阶段处理 |
| --- | --- | --- |
| 下载、预检、在线备份 | 中止，旧服务继续运行 | 中止，现有节点继续运行 |
| 新应用启动/验证失败，无不兼容写入 | 恢复旧镜像，验证后撤销维护 | 候选摘除并恢复旧镜像，另一节点继续服务 |
| 公网入口验证失败 | 区分 DNS/代理与应用故障，再按状态恢复 | 恢复入口配置，保留健康节点；不盲目重复更新 |
| 迁移开始后失败或兼容性未知 | 保持维护，进入明确恢复流程 | 停止更新，必要时维护，不混跑未知版本 |
| 数据库/文件恢复 | 确认恢复点和之后新增数据处理方案 | 相同，不能靠负载切换解决 |

备份恢复不是普通 rollback 的默认步骤。需要恢复数据库时，列明恢复点后的新增遥测、配置、账号及文件如何保留或重放；设备缓存无法恢复所有管理操作。备份建议保留最近 7 次成功发布副本和 30 天日备份，按实测磁盘调整，并安排异机副本与恢复演练；调度任务待实施时另行建立，本轮未创建自动任务。

## 9. 命令与文件改造设计

single、maintenance、plan和verify已实现；rolling仍未实现且会被拒绝。deploy-plan只检查已暂存/已拉取的候选。下表保留完整设计范围：

| 设计入口 | 作用 |
| --- | --- |
| make deploy-plan VERSION=... | 只读检查目标版本、兼容性、资源、基础服务差异，输出路径和预期窗口 |
| make deploy VERSION=... MODE=single | A 阶段普通发布，在线备份后替换应用 |
| make deploy VERSION=... MODE=rolling | B 阶段逐节点发布，未通过集群门槛时拒绝 |
| make deploy VERSION=... MODE=maintenance FROM_VERSION=... | 明确维护升级，不推断迁移路径 |
| make deploy-status | 增加实际节点版本、发布阶段、维护状态和就绪摘要 |
| make rollback VERSION=... | 检查兼容清单和实际结构，只回退允许的应用版本 |
| make deploy-verify | 验证入口、登录、专用测试设备遥测、产量和大屏 |

保留现有 make deploy 默认入口；当前默认请求single，未知旧镜像自动转maintenance；不能自动根据内存猜测并开启 rolling。首次安装沿用独立 install 分支。

| 文件范围 | A 阶段改动 | B 阶段追加 |
| --- | --- | --- |
| scripts/deploy-remote.sh | 在线备份、分类发布、基础服务隔离、状态日志、恢复协议 | 节点排空、逐节点更新、流量控制 |
| scripts/deploy.sh / Makefile | 发布清单、plan/verify 入口、验证报告 | rolling 参数及集群门槛 |

| deploy/Caddyfile | 维护 API、稳定配置挂载及校验/reload流程 | 双上游、健康检查、WS策略、静态资源 |

## 10. 验收与推进顺序

### A 阶段验收

- 在线备份成功与失败各演练一次；失败不停止旧服务。独立库完整恢复后设备、遥测、产量、大屏链接可读取。
- 普通发版不会重建 PostgreSQL/Caddy，空库安装与维护升级路径仍正确；回退不覆盖新数据。
- 相似数据量下测量至少 3 次发布的备份耗时、停止耗时、启动耗时和真实不可用区间；报告 P50/最慢值，不只报告脚本结束时间。
- 持续采集测试设备按 2 秒发送，覆盖停机期间清零、跨班次、断电重启、重复补报和乱序；原始记录及产量与基准逐条比对。
- 故意让新版启动失败、断 SSH、连续信号中断，验证阶段恢复、部署锁释放与旧服务恢复。
- 大屏已打开/首次打开、JWT 过期、iframe、恢复后轮询均验证；不把断线时的旧速度显示成实时。
- 无缓存设备明确登记，完整性目标仅对通过持久缓存与确认验收的设备成立；内存队列缺口通过原始数据修复或标记。

### B 阶段验收目标（待压测证明）

- 一节点可独立承载峰值业务，候选启动与备份并发时无 OOM，内存至少保留约 20% 余量，队列积压可收敛。
- 常规兼容更新，持续关键 HTTP 探测目标为零失败；业务请求错误率不高于更新前基线，不能通过代理隐藏写入失败。
- MQTT/WS 允许下线节点的连接重建，目标 60 秒内恢复受影响客户端；前提是客户端重连参数受控。
- 缓存容量内、原始记录可用的测试设备最终样本无缺失，重复不增加产量；默认目标 5 分钟内补报/统计收敛，超量时按负载模型重新设定。
- 跨节点登录、遥测订阅、RPC、凭据重置、产量回算/配置和匿名大屏权限全通过。
- 回退、Kafka暂不可用、数据库延迟、候选节点故障、旧前端懒加载均有独立演练。

实施顺序：A1 发布分类/在线备份/状态恢复 → A2 大屏线上核对与遥测缺口修复 → A3 代表性设备缓存确认协议与补报演练 → B1 容量压测和基础设施迁移设计 → B2 集群与产量并行验证 → B3 HTTP/MQTT入口迁移及滚动更新。

开始实施 A 不依赖购买新服务器。设备缓存能否由现有固件/网关实现、设备数量与峰值、容忍延迟、备份实际体量，以及 B 阶段资源预算在实施中核对；这些未确认项不阻止先改发布脚本。所有阶段完成本地/预发布演练后，才按对应范围进行生产变更。
